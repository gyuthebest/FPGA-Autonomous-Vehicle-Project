## 1. 골든 모델 완성

### 1.1 왜 필요했나

`compare_golden_vs_pl.py --board` 는 채널 11개의 상태를 전부 비교하는데,
모델은 관계식 3/4/5/9/10/11/12/13/15/16/17 을 구현하지 않고 있었다.
비교기가 **모델이 계산하지 못하는 값을 조용히 비교**하고 있었던 것이다.

```
시작 (모델 미완성)                     불일치 11.526%  (4,492 / 38,973)
관계식 전부 + 마스크 1~8 구현 후        불일치  1.586%  (618, gyro_z 만)
관계식 17 의 16비트 곱 절단 반영 후     불일치  0.000%  (0 / 38,973)
```

### 1.2 구현한 것

| 항목 | 내용 |
|---|---|
| pred 기준값 | accel_x/y/z 의 1·2·3, gyro_*_2, gyro_z_3, approach_speed |
| 기하 LUT | sin / cos / tan / steer (25·25·25·14 엔트리, 선형 보간) |
| 중력 성분 | grav_x/y/z, `approx_sqrt` 시프트 근사 |
| 마스크 | consistency_mask_1~8, `untrusted_*`, mask_20s(400표본) |
| 저장 폭 | `pred_data_t` 각 필드 폭으로 절단 (`_trunc`) |
| 되먹임 | timeout_mask_1s / cons_1s / cons_20s → preprocessor, `win`(M=100) |

### 1.3 함께 잡은 모델 전사 오류 4건

| # | 내용 | 영향 |
|---|---|---|
| 1 | accel_y/accel_z 의 stuck 트리거가 `delta_speed_x` 로 되어 있었다 | RTL은 축별 `delta_speed_y/z` |
| 2 | approach_speed 의 stuck 트리거가 `delta_approach_speed` | RTL은 `delta_distance − prev_delta_distance` |
| 3 | timeout 마스크를 **감쇠 후** 값으로 읽었다 | 복구 첫 표본이 noise 이력에 들어갔다. RTL은 레지스터 출력이라 감쇠 전 값을 쓴다 |
| 4 | 무표적 sentinel 이 approach_speed 진단까지 마스크 | RTL은 distance 만 마스크. approach_speed 의 0 은 실제 측정값이라 진단이 유효하다 |

### 1.4 상태 판정식 확정

두 규칙이 경합했다.

```
구조적 (RTL) : (r || t || (s && c)) -> INVALID,  (j || n || (s ^ c)) -> DEGRADED
고장 개수     : (t || 고장>=2)       -> INVALID,  (고장==1)          -> DEGRADED
```

실보드 대조가 갈랐다.

| 규칙 | 불일치 |
|---|---|
| **구조적** | **0 / 38,973** |
| 고장 개수 | 1,341 / 38,973 (accel_x 124, accel_y 386, accel_z 5, gyro_z 826) |

골든 모델을 구조적 규칙으로 확정했다.
`range` 단독을 INVALID 로, `jump`+`noise` 를 DEGRADED 로 보는 것은
"물리 범위를 벗어난 값은 못 쓴다 / 흔들림은 제한적으로 쓴다"는 해석과 일치한다.
**다만 사양 문서(구글 독스 표1)와의 최종 대조는 남아 있다.**

## 2. 발견한 RTL 결함 3건

### 2.1 `pred_gyro_z_3` 곱셈 폭 (관계식 17) — 실측으로 확정

```systemverilog
pred_data_out.pred_gyro_z_3 <= (sim_data_in.speed_x * steer_lut_val) >>> LUT_SH;
```

Verilog 는 곱셈 결과 폭을 `max(피연산자, 문맥)` 으로 정한다. **합이 아니다.**
LHS 가 `signed [15:0]` 이므로 14비트 × 12비트 곱이 **16비트로 wrap된 뒤**
시프트된다.

```
2240 × (-184) = -412,160  ->  16비트 절단 -18,944  ->  >>>10 = -19   (정상값 -403)
```

관계식 17(조향 기반 예상 요각속도)은 사실상 "요각속도 ≈ 0" 검사로 퇴화해 있었다.
이미 고친 `pred_gyro_*_1` 16→28비트와 **같은 종류의 버그**다.

**증거**: 이 절단을 모델에 넣으면 실보드 불일치가 618 → **0** 이 된다.
넣지 않으면 618건이 남고, 그 618건은 전부 gyro_z 이며 양방향으로 발생한다
(모델 DEGRADED/보드 NORMAL 과 그 반대가 섞여 있다 = 디바운스 위상 차이).

### 2.2 `pred_accel_y_3` 곱셈 폭 (관계식 15) — 잠복

```systemverilog
pred_data_out.pred_accel_y_3 <= (sensor_data_in.accel_z * tan_x) >>> LUT_SH;
```

12비트 × 12비트, LHS 12비트 → 12비트 곱. `980 × 608 = 595,840` 이 wrap 된다.
주행 중에는 `consistency_mask_5 = (situation != 0) | ...` 로 가려져 이번
캡처에서 발현되지 않았다. **경사면 정차 시 나타난다.**

`pred_accel_x_3` 은 같은 형태지만 `approx_sqrt` 가 32비트라 문맥이 32비트가
되어 안전하다. 우연히 살아 있었던 것이다.

### 2.3 관계식 4 의 구심항 누락 — 물리 모델 결함

```
기존 기준값 : a_y = dv_y/dt + g_y
실제        : a_y = dv_y/dt + g_y + v_x·ω_z     (구심가속도)
```

정상 선회에서 차체 좌표계 횡속도는 거의 변하지 않아 `dv_y/dt ≈ 0` 인데
실제 `a_y` 는 `v_x·ω_z` 만큼 나온다. **정상 선회가 그대로 고장으로 판정된다.**

실캡처 3,543표본 잔차 (임계 TH_ACC = 76):

| 기준값 | 중앙값 | p90 | 최대 | 임계 초과 |
|---|---|---|---|---|
| 현행 (구심항 없음) | 111 | 268 | 504 | 55.8% |
| 구심항 `/1000` | 7 | 22 | 133 | 0.53% |
| 구심항 `>>> 10` | 8 | 23 | 124 | **0.65%** |

`>>> 10` 은 정확한 1/1000 보다 2.4% 작지만 오차 최대 12 raw 로 임계 76 대비
무시할 수 있고 **곱셈기를 추가하지 않는다.** 이 쪽을 채택했다.

### 부수 발견 2건 (미해결)

**yaw ±180° 경계 미처리.** 관계식 8 의 잔차 최대가 128,667,794 인데
이는 `36000 × C_GYR(3574) = 128,664,000` 이다. `incline_z` 가 ±180° 를
넘는 순간 차분이 36000 이 되어 gyro_z consistency 가 순간적으로 깨진다.
이번 캡처에서 2회(seq 679, 2529) 발생했다. 각도 wrap 처리가 없다.

**lux stuck.** `u_chk_lux` 는 `CHANNEL_TYPE_2 = 0` 이라 항상 testable 이고
`STUCK_N = 15` 다. 맑은 날 조도가 일정하면 stuck 으로 확정된다.
이번 캡처에서 delta==0 최장 연속이 **149표본**(7.5초)이었고 lux 오탐 6.94%
전부가 stuck 이다. 환경 채널은 정상적으로 일정할 수 있다.

### 6.8 라이브 시나리오 회귀 (보드)

`CARLA_LIVE_VERIFY=1` → `CARLA LIVE CONTROL RESULT: **PASS=71 FAIL=4**` / 75건
로그: `live_scenarios_after_fixes.log`, 캡처 `pl_capture_20260814_154327.csv`

실패 4건은 전부 원인이 규명됐고 **RTL 문제가 아니다.**

**(a) collision_caution / collision_danger — 시나리오가 물리적으로 모순된 입력을 넣는다**

`world_scenario_controller.py` 는 충돌 tier 를 만들 때 접근속도를 10 m/s 로
두고 **거리를 고정**한다 (tier 1 = 35 m, 2 = 25 m, 3 = 18 m, 4 = 12 m).
10 m/s 로 접근하는데 거리가 변하지 않는 것은 불가능하다. PL 은 이를 정확히
잡아낸다.

| seq | 거리 | 판정 |
|---|---|---|
| 73 | 20000 → 3500 (한 표본에 165 m 도약) | noise 확정 → distance DEGRADED |
| 83~90 | 3500 고정, 접근속도 1000 | **stuck 확정** |
| 91~96 | 관계식 1(거리 예측) 도 확정 | 고장 2개 → **distance INVALID** |

distance 신뢰도가 떨어지자 `risk_control` 이 충돌 tier 를 보수적으로
올렸다(1 → 2 → 3). **이것은 "신뢰도 기반 위험도"의 설계 의도대로 동작한 것**
이며, 시험이 기대한 원시 tier 와 어긋났을 뿐이다.

골든 모델도 같은 판정을 낸다(2표본 위상차 제외). 즉 구현 문제가 아니다.

**(b) sensor_distance_stuck / sensor_approach_speed_stuck — 교차 게이팅 사각지대**

| 사례 | 주입 상태 | 미검출 이유 |
|---|---|---|
| distance:stuck | 거리 8000 고정, 접근속도 **8**(0.08 m/s) | 거리 stuck 은 `cond_b = \|approach_speed\| >= STUCK_THRESHOLD(20)` 이 조건이다. 8 < 20 이라 **testable 이 아니다** → 증거가 쌓이지 않는다 |
| approach_speed:stuck | 접근속도 8 고정, 거리 ±8 진동 | 거리를 흔들어 trig 을 만들었는데 그 진동이 distance 를 DEGRADED 로 만들고, `stuck_mask_1s_or_20s[CH_APSP]` 가 distance 고장을 OR 하므로 **stuck 검사가 마스크된다** |

이 2건은 **오늘 변경 이전에도 간헐적으로 실패했다** (과거 로그에 PASS/FAIL
혼재). 회귀가 아니다.

교차 게이팅 자체("기준 채널이 망가졌으면 stuck 판정을 믿지 않는다")는 타당한
설계지만, **기준 채널이 degraded 이면 stuck 검사가 조용히 꺼지는 사각지대**가
생긴다. 정지한 표적(접근속도 ~0)에 대해 고착된 레이더는 원리적으로 검출되지
않는다. 아래 7절에 남긴다.

### 새로 발견했고 아직 손대지 않은 문제

**1. yaw ±180° 경계 미처리.** 관계식 8 의 잔차 최대가 128,661,992 로
`36000 × C_GYR(3574) = 128,664,000` 에 해당한다. `incline_z` 가 ±180° 를
넘는 순간 차분이 36000 이 되어 gyro_z consistency 가 순간적으로 깨진다.
수정 전 캡처에서 2회(seq 679, 2529) 발생했다. 각도 wrap 처리가 없다.
`delta_incline_z` 를 ±18000 기준으로 되감으면 해결된다. **미승인.**

**2. lux stuck 오탐 6.39%.** `u_chk_lux` 는 `CHANNEL_TYPE_2 = 0` 이라
항상 testable 이고 `STUCK_N = 15` 다. 맑은 날 조도가 일정하면 stuck 으로

환경 채널(온도/습도/조도)은 정상적으로 일정할 수 있으므로,
stuck 판정에 "환경이 변하고 있을 때만" 같은 조건이 필요하다. **미승인.**

**3. accel noise 오탐 5~7%.** `NOISE_THRESHOLD_1 = 500`(accel) 대비
주입 잡음이 크다. 잡음 모델의 진폭이 실센서 기준으로 타당한지,
아니면 임계값을 올려야 하는지 확인이 필요하다. **미승인.**

**4. stuck 교차 게이팅 사각지대.** 6.8(b) 참조.
거리 stuck 은 접근속도가 0.2 m/s 이상일 때만, 접근속도 stuck 은 거리가
정상일 때만 검사된다. **정지 표적을 향한 고착 레이더는 원리적으로 검출되지
않는다.** 설계 의도(기준 채널이 망가지면 판정을 믿지 않는다)는 타당하나,
검사가 꺼졌다는 사실이 밖으로 드러나지 않는 것이 문제다.
"검사 불가" 상태를 별도로 표시하거나, 무표적/저속 구간에서는 다른 근거
(예: 레이더 자체 헬스 신호)를 쓰는 방안이 필요하다. **미승인.**

**5. 충돌 시나리오 입력이 모순이다.** 6.8(a) 참조.
`world_scenario_controller.py` 가 접근속도 10 m/s 를 주장하면서 거리를
고정한다. 접근속도에 맞춰 매 표본 0.5 m 씩 줄이면 해결된다.
**시험 시나리오 수정이므로 RTL 과 무관하나, 소스 변경이라 미승인.**

## 8. 프로젝트 결론

### 8.1 구현 검증 — 완료

**"FPGA가 알고리즘을 그대로 구현했는가"에 대한 답은 확정적으로 '예'다.**

근거는 하나의 수치다. 실주행 자극 3,509프레임을 지터 없이 재생했을 때
보드의 신뢰도 판정이 골든 모델과 **38,379건 전수 일치**했다.
여기서 골든 모델은 RTL 전사가 아니라 관계식 17건·마스크 8종·검사기 5종을
사양에서 다시 구현한 독립 구현이며, 임계값 상수만 공유한다.

이 판정이 가능해진 것은 이번에 모델을 완성했기 때문이다. 관계식 9건이
비어 있던 상태에서는 불일치 11.5%가 RTL 오류인지 모델 미구현인지

부수적으로, 이 과정에서 **모델 자신의 전사 오류 4건**도 드러났다
(stuck 트리거 2건, timeout 마스크 위상 1건, sentinel 마스크 범위 1건).
독립 구현과 실보드를 맞대어야만 나오는 종류의 오류다.

검증된 것:

- 고장을 주입하면 **52건 중 51건을 잡는다.** 검출 지연 중앙 50 ms, 최악 0.9초.
- 복구도 된다. 중앙 0.55초, 최악 2.9초. 붙잡힌 채 안 풀리는 채널은 없다.
- 정상 주행에서 **INVALID 오탐은 0건**이다. 오탐은 전부 "사용제한" 등급이다.
- 위험도 시나리오 71건이 의도한 차량 명령을 만들어낸다.
- **폐루프에서도 판정이 발산하지 않는다.** PL 출력을 차량에 적용한 3분 주행의
  오탐률이 개루프와 같은 대역이고 INVALID 는 0건이다.

반증된 것 — **원래 알고리즘에는 정상 주행을 고장으로 판정하는 결함이 있었다.**

| 채널 | 수정 전 오탐률 | 원인 |
|---|---|---|
| accel_x | 70.14% | AXI 속도 8비트 압축 → 기준값이 6.4 m/s² 계단 |
| accel_y | 55.32% | 관계식 4 에 구심항 v_x·ω_z 누락 |
| gyro_z | 27.69% | `pred_gyro_z_3` 16비트 곱 wrap |

세 원인 모두 **파라미터가 아니라 구현·인터페이스 문제**였다는 점이 중요하다.
임계값(`TH_ACC=76`, `TH_GYR_STEER=120`)은 하나도 바꾸지 않았고,
바꾼 것은 기준값의 정확도뿐이다. 수정 후 같은 임계값에서
오탐률이 9.57% / 7.14% / 2.87% 로 떨어졌고, **잔차 중앙값이 임계값을 넘는
관계식이 하나도 남지 않았다.**

이는 "임계값을 실측으로 완화한다"는 흔한 대응과 정반대 방향의 해결이다.
`TH_GYR` 을 270 → 7300 으로 올렸던 이전 조치도 같은 눈으로 다시 볼 필요가 있다.

### 8.3 남은 약점

수정 후에도 오탐이 5~10% 남아 있고, **성격이 바뀌었다.**
consistency 가 아니라 **noise 검사와 lux stuck** 이 지배한다(6.7절).
이는 임계값/잡음모델 문제이며 별도 판단이 필요하다.

구조적으로 남은 것 3가지:

1. **stuck 교차 게이팅 사각지대** — 정지 표적을 향한 고착 레이더는 원리적으로
   검출되지 않는다. 안전 관점에서 가장 무거운 항목이다.
2. **yaw ±180° 경계 미처리** — 각도 wrap 때마다 gyro_z consistency 가 깨진다.
3. **관계식 1·9~16 미검증** — 무표적/주행 상태라 이번 자극에서 활성화되지
   않았다. 정지·경사면 자극이 필요하다.

### 8.4 검증 체계에 대한 평가

이번에 드러난 것은 **검증 도구 자체의 결함이 결과를 왜곡하고 있었다**는 점이다.

- 비교기가 모델 미구현 항목을 조용히 비교했다 → 불일치 11.5% 의 정체 불명
- 빌드 스크립트의 DRC 게이트가 문법 오류로 한 번도 실행되지 않았고,
  **bitstream 을 쓴 뒤 XSA 를 쓰기 전에 죽어** XSA 가 낡을 수 있었다
- 합성 스모크 자극이 단조로워 accel/gyro consistency 경로를 건드리지 못했다
- 실주행 캡처 대조는 호스트 지터에 오염되어 있었다(불일치 32건 전부 지터 근처)

네 가지 모두 이번에 고쳤고, 마지막 항목은 "추정하지 않고 상관을 보고한다"는
형태로 정직하게 남겼다. 지터 없는 재생 경로(`--replay`)를 새로 만든 것이
비트 정확성 판정을 가능하게 한 결정적 변경이다.

### 8.5 2차 작업 — 미검증 항목 축소 (같은 날 추가)

사용자 지시로 남은 검증 공백 중 넷을 닫았다. **RTL 은 건드리지 않았다**
(재빌드 불필요, 현재 bitstream 그대로).

**(1) 상태 판정식 확정** — 사용자가 구조적 방식이 맞다고 확인했다.
`(r||t||(s&&c)) → INVALID, (j||n||(s^c)) → DEGRADED`. 미결 항목에서 제거.

**(2) TD/MRM 타이머 골든 모델 구현** — `risk_control.sv` 의 유효 tier 계산
(`calc_effective_tier`), 9개 위험도 그룹 신뢰도, HUD 조건, 1초 TD 타이머,
`td_locked` / `td_invalid_duration` / MRM 을 모두 구현했다.
비교기가 이제 **risk 워드(read_reg9)와 HUD/TD/MRM 을 실제로 대조한다.**
지금까지 이 4개 출력은 비교 범위 밖이었다.

| 캡처 | risk 워드 | HUD | MRM | TD 잔여초 |
|---|---|---|---|---|
| 개루프 152339 | 99.80% | **100%** | **100%** | **100%** |
| 라이브 154327 (지터 반영) | 87.86% | **100%** | **100%** | 98.14% |

라이브 캡처에서 보드 TD 카운터가 실제로 11→10→9→8→7 까지 내려갔고
HUD 는 382표본 동안 떴다. **TD 불일치 80건은 전부 정확히 ±1초**다.
로직 오류라면 값이 발산하거나 5초 lock 을 놓쳤을 텐데 그렇지 않다.
`sec_cnt` 는 PL 클럭 자유 카운터라 표본과 동기가 아니고, 그 위상은
호스트 로그로 복원할 수 없다 — 구조적 한계이며 문서화했다.
risk 워드 불일치는 신뢰도 불일치(지터)의 하류 결과다.

**중요한 부수 효과**: 지금까지 `classify_risk()` 의 **원시 tier** 로
보드의 risk 워드를 해석하려 했기 때문에 6.8(a) 충돌 시나리오 분석이
혼란스러웠다. 보드가 내보내는 것은 **신뢰도 반영 유효 tier** 이고,
이제 모델이 그것을 직접 계산한다.

**(3) transport timeout — 사용자 제안대로 결정론적 시험 확보**

> "센서 데이터는 들어와도 sample_seq 를 그냥 안 붙여주는 방법을 쓰면
>  timeout check의 문제도 단순하게 해결되지 않나?"

맞다. `valid_s0 = (sample_seq_in != sample_seq_out)` 이므로 프레임은 계속
보내되 `sample_seq` 만 고정하면 PL 은 "새 표본 없음"으로 보고
`timeout_phase_cnt` 가 100 ms 마다 `raw_timeout` 을 낸다. UDP 를 끊거나
지터를 기다릴 필요가 없고 호스트가 지속 시간을 정확히 통제한다.

`board_smoke_test.py --timeout-test` 로 구현했다. 실측:

```
보류 전                 rel = 0x150000
보류 40프레임 (2초)      응답 40/40, rel 갱신 없음
재개 +1 표본            rel = 0x2AAAAA  INVALID 11/11  (골든 모델 11/11)
재개 후 기준선 복귀       2 표본
결과: PASS
```

**관측 지점에 함정이 있었다.** AXI 로 나오는 신뢰도 워드는
`risk_control` 의 `rel_out` 이고 `valid_in_rel` 에서만 래치된다. 그래서
보류하는 **동안에는 워드가 갱신되지 않고**, 확정된 timeout 은
**재개 첫 표본**에서 처음 드러난다. 처음에 보류 중을 관측하도록 짰다가
"INVALID 0/11" 로 실패했고, 5초까지 늘려도 같았다. 원인을 PS 브리지
캐싱으로 의심했으나 `ps_carla_bridge.c:83-86` 은 매번 레지스터를 새로
읽는다. 실제 원인은 위 래치 구조였다.

이로써 **timeout 경로가 처음으로 보드에서 검증됐고 골든 모델과 일치한다.**

**(4) 관계식 9~16 — 처음으로 활성화**

`make_trace_vectors.py` 에 `standstill_slope` 시나리오를 추가했다.
경사면(incline 5.0°/3.0°) 정차라 `situation == 000` 이 되어
`consistency_mask_4/5/6` 이 열린다. 실주행 캡처 3,489표본에서 이
관계식들의 active 표본이 **0** 이었던 이유가 바로 이 마스크다.

`run_offline_verification.bat` 의 골든-vs-RTL 목록에 상시 포함시켰다.

비교기에 `cons_accel_x`(관계식 3/9/16)와 `cons_distance`(관계식 1) 판정
비트를 추가했다. 이 두 신호는 트레이스에 있었는데 **아무도 비교하지
않고 있었다.**

**(5) TH_ACC_STOP = 4 — 내 예측이 틀렸다**

앞서 "관계식 3/4 와 같은 양자화 바닥 패턴으로 의심된다"고 적었다.
검증해 보니 **틀렸다.** 깨끗한 정차 자극(잡음 없음, 실제 삼각함수 입력):

| 관계식 | 채널 | 임계 | 잔차 중앙 | 잔차 최대 | 판정 |
|---|---|---|---|---|---|
| 9 | accel_x | 4 | 0 | 0 | 통과 |
| 10 | accel_y | 4 | 1 | 1 | 통과 |
| 11 | accel_z | 4 | 1 | 1 | 통과 |
| 12/13/14 | gyro_x/y/z | 4 | 0 | 0 | 통과 |
| 15/16 | accel_y/x | 43 | 1 | 1 | 통과 |

11비트 LUT + 선형보간의 양자화 바닥은 **1 raw(0.01 m/s²)** 에 불과하다.
`TH_ACC_STOP = 4` 는 적절하며 **변경할 필요가 없다.**

앞서 실캡처에서 관측한 80% 초과는 (a) `situation` 이 speed ≤ 1 km/h 로
판정되어 **감속 과도 구간**이 포함됐고 (b) 라이브 캡처의 자세/고장 주입이
섞였기 때문이다. 무주입 필터를 걸어도 35표본 전부가 정지 진입 순간이었다.
**35표본짜리 과도 데이터로 안전 임계값을 정하지 않은 것이 옳았다.**

### 8.6 노이즈 강건성 시험 설계 (다음 단계)

목표: 깨끗한 주행 데이터와 잡음 가미 데이터를 비교해 시스템 강건성을 본다.

**주의 — 현재 "깨끗한" 기준선이 없다.** 오늘 캡처 3개 전부
`[SENSOR NOISE] enabled` 상태였다. 비교하려면 먼저 `CARLA_SENSOR_NOISE=0`
으로 무잡음 기준 주행을 떠야 한다.

**잡음 여유는 이미 측정됐다.** 정차+경사에서 현재 잡음모델을 켜면:

| 관계식 | 임계 | 잔차 중앙 | p90 | 최대 | 임계 초과 | 채널 오탐 |
|---|---|---|---|---|---|---|
| 9 (accel_x) | 4 | 2 | 3 | 4 | 0.0% | 0% |
| 10 (accel_y) | 4 | 2 | 4 | 5 | 3.9% | 0% |
| 11 (accel_z) | 4 | 2 | 4 | 5 | 1.1% | 0% |
| 12~14 (gyro) | 4 | 2~3 | 4 | 4 | 0.0% | 0% |

원시 위반이 3.9% 나와도 **채널 오탐은 0%** 다. `N_CONS=8 / D_CONS=3` 디바운스가
산발적 위반을 흡수한다. 다만 p90 이 임계값과 같아 여유가 얇다.

**따라서 잡음 진폭을 지금의 약 2배로 올리면 관계식 10/11 이 확정되기
시작한다.** 이것이 강건성 시험의 자연스러운 스윕 범위다.

권장 설계:

1. 기준선: `CARLA_SENSOR_NOISE=0` 개루프 3분 → `pl_capture_metrics.py`
2. 잡음 배율 1.0 / 1.5 / 2.0 / 3.0 배로 각각 3분
3. 각 배율에서 채널별 오탐률, 관계식별 확정률, 검출 지연을 산출
4. 판정 기준은 **오탐률 곡선의 무릎(knee)** — 어느 배율에서 급증하는가
5. 동시에 `fault_latency_metrics.py` 로 **검출률이 유지되는지** 확인한다.
   잡음이 늘면 오탐만 느는 게 아니라 임계값 여유가 줄어 검출도 빨라진다.
   강건성은 "오탐은 안 늘고 검출은 유지" 여야 의미가 있다

배율 조절은 `sensor_noise.py` 의 진폭에 스칼라를 곱하는 환경변수
(`CARLA_SENSOR_NOISE_SCALE`) 하나면 충분하다. **아직 만들지 않았다.**

비교 도구는 이미 다 있다. `pl_capture_metrics.py` 가 캡처마다 채널별
오탐률과 관계식별 잔차 분포를 JSON 으로 떨구므로, 배율별 JSON 을 나란히
놓으면 그대로 강건성 곡선이 된다.

### 8.6.2 노이즈 강건성 — 실행 결과

**(a) 환경 채널 바닥 진동 (사용자 지시)**

> "온도, 습도, 조도는 노이즈 있는 시나리오나 없는 시나리오나 모두 약간의
>  노이즈가 포함되어야 한다. 약간의 노이즈가 있어야 신뢰도 NORMAL이 뜨기 때문이다."

무잡음 기준선을 떠서 확인했다. **지적대로였다.**

| 채널 | `CARLA_SENSOR_NOISE=0` (바닥 진동 도입 전) |
|---|---|
| temperature | **100.00% DEGRADED** |
| humidity | **100.00% DEGRADED** |
| lux | **93.32% DEGRADED** |

전부 stuck 이다. 이 세 채널은 `CHANNEL_TYPE_2 = 0` 이라 항상 testable 이고
`STUCK_N = 15` 라, 값이 일정하면 15표본 만에 확정된다.

`sensor_noise.py` 에 **바닥 진동**을 넣었다. 계측 잡음과 달리
`CARLA_SENSOR_NOISE=0` 에서도 적용되고 `SCALE` 배율도 받지 않는다.
파형은 주기 8 삼각파(raw −2,−1,0,1,2,1,0,−1).

| 성질 | 실측 | 한계 |
|---|---|---|
| `delta == 0` 개수 | **0** | stuck 이 누적되지 않는다 |
| 10창 부호 반전 | 2 | `NOISE_THRESHOLD_2` = 7 |
| 10창 \|delta\| 합 | 10 | 온습도 `NOISE_THRESHOLD_1(2)×10` = 20 |
| \|Δ − prevΔ\| 최대 | 2 | `JUMP_THRESHOLD` = 5 |

물리 진폭은 온도 ±0.2 °C, 습도 ±2 %, 조도 ±2.
도입 후 세 채널의 오탐률은 **0.00%** 가 됐다.

`test_scenario_pl_alignment` 의 `test_disabled_model_is_a_no_op` 가 이전
정책("비활성이면 완전 무변경")을 인코딩하고 있어 실패했다. 통과시키려고
조건을 무르게 하지 않고, 운동 채널이 여전히 무변경임을 확인하도록 좁힌 뒤
바닥 진동의 네 가지 성질을 실제로 검사하는 시험을 신규 추가했다.

**(b) 방법론 — 배율마다 다시 주행하면 안 된다**

배율 OFF/1.0/2.0/3.0 으로 각각 3분씩 CARLA 주행해 비교했더니 곡선이
단조롭지 않았다.

```
accel_x 오탐률   10.19%  ->  14.92%  ->   6.08%  ->  20.25%
```

운동 채널 오탐은 잡음보다 **그 주행의 선회·가감속**에 더 크게 좌우된다.
CARLA autopilot 은 같은 궤적을 보장하지 않으므로 이 비교는 강건성이 아니라
주행 차이를 보여준다.

그래서 `noise_injection_sweep.py` 를 만들었다. **무잡음 캡처 하나를 기준
궤적으로 고정**하고 그 물리값에 계측 잡음만 배율을 바꿔 다시 입혀 REG 워드를
재합성한다. 궤적·날씨·조향이 동일하므로 차이는 오직 잡음에서 온다.
(기준 캡처에 이미 바닥 진동이 있으므로 재주입 시 계측 성분만 더한다.)

**(c) 통제 실험 결과** — 기준 궤적 `pl_capture_20260814_170103.csv`, 3,416표본

**INVALID 은 x4 까지 전 배율에서 0건이다.** 잡음이 4배가 되어도 어떤 채널도
"사용 불가"로 떨어지지 않는다. 위험도 판정이 멈추지 않는다는 뜻이다.

**강건성 한계는 x2.0 이고, 그것을 정하는 것은 온도/습도의
`NOISE_THRESHOLD_1 = 2` 다.** 바닥 진동이 10창 합 10을 이미 쓰고 있어
한계 20까지 여유가 10뿐이다. x2 에서 계측 잡음이 그 여유를 먹는다.

**(d) 운동 채널은 잡음을 늘릴수록 오탐이 준다 — 원인 규명**

accel_y 가 11.50% → 2.58% 로 **감소**한다. 관계식 4 는 전 배율에서 0.00%
이고 관계식 3 도 4.63% → 4.86% 로 평평하다. 즉 consistency 가 아니다.

범인은 `NOISE_THRESHOLD_2` — **10표본 창 안의 부호 반전 7회 초과**다.
`NOISE_THRESHOLD_1` 은 accel 기준 500(10창 합 5000 = 50 m/s²)이라 걸릴 수가 없다.

`delta_accel_y` 의 부호 반전을 직접 세어 확인했다.

| 배율 | 10창 반전 중앙 | 반전 > 7 비율 | accel_y 오탐률 |
|---|---|---|---|
| OFF | 3 | **11.5%** | **11.50%** |
| x1 | 3 | 7.8% | 7.76% |
| x3 | 2 | **2.9%** | **2.87%** |

**수치가 그대로 일치한다.** CARLA 가속도계 신호는 평균 주변에서 진동하므로
잡음이 없어도 부호가 자주 뒤집힌다. 그런데 이 프로젝트의 잡음 모델은
**저주파**(느린 사인 합성)라, 더할수록 delta 가 매끄러운 추세에 지배되어
**부호 반전이 오히려 줄어든다.**

이건 두 가지를 뜻한다.

1. `NOISE_THRESHOLD_2 = 7` 이 정상 주행 가속도계 신호에서 이미 10%대로
   걸린다. 남은 오탐의 주범이며 임계값 재검토 대상이다.
2. **현재 잡음 모델로는 부호 반전 판정을 시험할 수 없다.** 강건성 스윕이
   이 검사기를 전혀 스트레스하지 못한다. 백색 성분을 섞어야 의미가 생긴다.

**(e) 아직 안 한 것**

강건성은 "오탐이 안 늘고 **검출은 유지**" 여야 의미가 있다. 배율별
고장 주입(`CARLA_LIVE_VERIFY=1` + `fault_latency_metrics.py`)은 아직
돌리지 않았다. 다만 (c)에서 x2 부터 온습도 배경 잡음이 임계에 닿으므로,
**그 배율에서 온습도 noise 검출은 변별력을 잃는다**는 것은 이미 말할 수 있다.

### 8.7 한 줄 결론

**FPGA 구현은 검증됐다. 알고리즘은 이번 수정으로 정상 주행 오탐률이
70% → 9.6% 로 떨어졌고 고장 검출률 51/52·검출 지연 중앙 50 ms 를 달성했으나,
잡음 임계값과 stuck 교차 게이팅 사각지대는 미해결로 남는다.**
